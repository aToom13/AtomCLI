Atomic Work starts only through the native /atomic-work <goal> command. Its durable ledger is authoritative:
- action="plan": inspect code, provide bounded tasks with id, prompt, agent, dependsOn, owns, skills, budget, isolation, and nonempty acceptance. Shared foundations precede consumers; overlapping ownership requires dependency ordering. Use real agent/skill names and isolation="auto" without Git. Supply global integration acceptance; reserved global-goal criteria require parent runtime evidence by default, reviewer only with explicit opt-in.
- action="execute": await the existing orchestrate scheduler. At most four independent tasks run together; uncertain ownership or a non-git project serializes dispatch. A child result is submitted, never accepted by its own completion claim.
- action="status": read root ID, task IDs, versions, definitions, checks, evidence, and pending messages.
- action="verify": parent checks need criterionID, verifier="parent", passed, evidence, and runtime={criterion, setup, action, expected, observed, evidence:[{tool:"browser"|"bash", input:"exact tool arguments as JSON", output:"exact raw output excerpt"}]}. criterion must match the acceptance description exactly. Passing checks require successful tool calls after this revision's submission, a relevant test run or browser interaction followed by assertion/evaluation. Static searches, screenshots and no-op commands cannot prove behavior. Automatic commands and reviewer checks are run by the harness; parent claims cannot forge them. Reviewer/parent criteria never have command fields. Missing criteria keep work unaccepted.
- action="revise": provide expectedVersion and changed definitions. For one task, use task_id and definition (goal, agent, dependsOn, acceptance, execution); expectedVersion refers to that task. For a batch, expectedVersion refers to the root and each existing tasks entry also needs its expectedVersion. New tasks need no version. Changed work and downstream consumers reopen together; independent accepted tasks remain accepted.
- Pending user messages pause dispatch, patch application, and completion. Classify each with amendment={messageID, classification:"amendment"|"status"|"stop", evidence}. Planned amendments require changed definitions; before initial planning, classify first then plan the extended goal. Status preserves definitions; stop cancels execution.
- Retry limits survive restart. Exhaustion preserves checks and evidence until an explicit revision. Interrupted mutating work requires reconciliation before replay. Completion requires every implementation task and the integration root accepted, with no pending messages.

When to use the Task tool:
- When you are instructed to execute custom slash commands. Use the Task tool with the slash command invocation as the entire prompt. The slash command can take arguments. For example: Task(description="Check the file", prompt="/check-file path/to/file.py")

When NOT to use the Task tool:
- If you want to read a specific file path, use the Read or Find tool instead of the Task tool, to find the match more quickly
- If you are searching for a specific class definition like "class Foo", use the Find tool instead, to find the match more quickly
- If you are searching for code within a specific file or set of 2-3 files, use the Read tool instead of the Task tool, to find the match more quickly
- Other tasks that are not related to the agent descriptions above


Usage notes:
1. Launch multiple agents concurrently whenever possible, to maximize performance; to do that, use a single message with multiple tool uses
2. When the agent is done, it will return a single message back to you. The result returned by the agent is not visible to the user. To show the user the result, you should send a text message back to the user with a concise summary of the result.
3. Each agent invocation is stateless unless you provide a session_id. Your prompt should contain a highly detailed task description for the agent to perform autonomously and you should specify exactly what information the agent should return back to you in its final and only message to you.
4. The agent's outputs should generally be trusted
5. Clearly tell the agent whether you expect it to write code or just to do research (search, file reads, web fetches, etc.), since it is not aware of the user's intent
6. If the agent description mentions that it should be used proactively, then you should try your best to use it without the user having to ask for it first. Use your judgement.
7. **Automatic Progress Tracking**: When you call the Task tool, the TUI's Chain progress bar automatically updates to show the sub-agent's status (running, complete, failed). You do NOT need to manually call the chainupdate tool to track sub-agent progress — it happens automatically.
8. **Dynamic Sub-Agent Panel**: When a sub-agent is running, a dynamic panel appears on the right side of the TUI showing the agent's live activity (current tool, last output preview). The user can click on it to navigate to the sub-agent's session. This panel auto-shows and auto-hides.
9. **Session Reuse**: When re-tasking an agent, pass `session_id` from the previous result's metadata to continue in the same session. This keeps agents persistent and visible in the panel — they go to "waiting" state after each task and stay alive for new orders.
10. **Context Transfer**: Agents MUST return their full results (research findings, code output, analysis) in their final text response. This output is automatically passed back to the orchestrator for context-aware decision making. Do NOT just say "done" — return the actual content.
